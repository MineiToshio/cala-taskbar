# Architecture

Swift 5 language mode (`swift-tools-version: 5.9`), macOS 14+. SwiftPM executable target `Cala`. AppKit for windows and events, SwiftUI inside `NSHostingView` for the UI. Cala is a set of **modules** (Bar, Tray, Switcher, Zones) that start and stop on their own: see [Modules](#modules).

## Modules
Cala is four modules behind one protocol (`CalaModule`: `id`, `isRunning`, `start()`, `stop()`):

| Module | Owns |
|---|---|
| **Bar** (`BarModule` → `BarController`) | One panel per screen, the tick timer, the local event monitors, previews and peek, show desktop, space reservation, Dock and menu-bar hiding, the screen-change observer |
| **Tray** (`TrayModule`) | Wi-Fi, calendar, system monitor, disk, usage, mail, menu-bar icon hiding and the flyouts. **Depends on the Bar**: it only runs inside a running bar |
| **Switcher** (`WindowSwitcher`) | The Option+Tab (and optional Cmd+Tab / Cmd+M) `CGEventTap`, its 3 s retry timer, its panel |
| **Zones** (`ZonesModule`) | The drag tap and its thread, the worker queue, the overlay panels, the zones store; see [Zones](#zones) |

**Registry.** `ModuleRegistry` (main thread only) holds the desired `ModuleSet` (keys `barEnabled`, `switcherEnabled`, `trayEnabled`, `zonesEnabled` in `config.json`) and reconciles reality with it. A sink on `ConfigStore` re-applies whenever those keys change, so a Settings switch takes effect live. Applications are serialized: a change that arrives while one is running is coalesced and applied right after, using the latest value. `ModulePlan.effective` turns the tray off when the bar is off. `ModulePlan.startOrder` stops in the order Zones, Tray, Switcher, Bar and starts in the order Bar, Tray, Switcher, Zones, so the tray never outlives its bar.

**A stopped module holds nothing:** no monitors, timers, observers, event taps or windows (each module's `stop()` removes the ones its `start()` created; the debug log shows `module X: stopped`). The only things that outlive modules are the shell: `ConfigStore`, `PermissionCenter`, the Settings and welcome windows, feedback and crash reporting, the watchdog, the login item, the SIGTERM source and the status item controller.

**Shared thumbnail watcher.** `MinimizeWatcher` (AX observers and the 3 s sync timer) runs while the Bar **or** the Switcher runs (`ModulePlan.needsThumbnails`), because both need minimized-window thumbnails; it is created and torn down by the registry, not by either module.

**Dock and menu bar.** Hiding the macOS Dock and menu bar belongs to the Bar: `BarModule.start()` applies them, `stop()` restores them (on a real quit, according to `restoreDockOnQuit` / `restoreMenuBarOnQuit`). When Cala launches with the Bar off it touches nothing, except that it undoes a hidden Dock or menu bar a crash left behind (`DockControl.restoreAfterCrashIfNeeded`, `MenuBarControl.onBarStop`). Tray off restores any hidden macOS menu-bar icons.

**Status item.** `StatusItemController` shows a menu-bar icon when `!bar || zones` (so someone running only Zones or only the Switcher always has Settings and Quit), and removes it otherwise. Its menu is rebuilt each time it opens: Settings…, a Zones section (Zones editor… and one "*monitor*: *layout*" submenu per screen, with a picture of each layout at that screen's shape, when the module runs; the editor alone, with the layouts disabled, when it does not), Report a Problem… when there is no bar, Quit Cala.

**Startup and migration** (`ModulePlan.resolve`, pure and checked by `scripts/check-modules.sh`):
- Keys already stored (`modulesChosen`) win.
- An existing user (`onboardingCompleted`, or a `config.json` that existed at launch plus Accessibility, unless a first-run welcome was left unanswered) is migrated: Bar and Tray on, Switcher as stored (an old `switcherEnabled = false` is kept), Zones off, welcome not shown. Nothing is renamed: the new keys are added and `modulesChosen` is set.
- A fresh install runs **nothing** until the welcome's "What do you want to use?" is answered (Bar, Zones or both, at least one). The answer writes the module keys; `onboardingPending` (UserDefaults) marks an unanswered welcome, and `onboardingCompleted` is written only when the answer is saved, so quitting before choosing shows the welcome again. Only the chosen modules' permissions are requested.
- At launch the registry logs one line to the debug log: `modules: active=bar,switcher,tray off=zones source=migrated` (`source` is `stored`, `migrated` or `provisional (waiting for onboarding)`). Live changes log `modules: apply active=… off=… reason=…` and `module <id>: started` / `stopped`.

## Zones
Files in `Sources/Cala/Zones/`. The first group is pure (Foundation and CoreGraphics only) and compiled by `scripts/check-zones.sh`; the rest is AppKit.

| File | Role |
|---|---|
| `ZoneModel.swift` | `ZoneRect` (fractions), `Zone`, `ZoneLayout`, `ZonesState`, `ZoneActivation`, repair on load, duplicate and delete rules |
| `ZoneGeometry.swift` | Usable rectangle, fraction ↔ frame, gap insets, AppKit ↔ Accessibility flips, screen for a point, clamping |
| `ZonePicking.swift` | Zones under a point, the overlap rule, ⌘ span, the target frame, editor hit-testing and handles |
| `ZoneSnapping.swift` | Editor snapping candidates (edges, centre, 12-grid), move, resize and draw operations, guides |
| `ZoneTemplates.swift` | The eight templates and the first-run seed |
| `ZoneRestore.swift` | Snap records (bounded to 200), "still snapped?" and the restored frame that keeps the grab point |
| `ZoneDisplayKeys.swift` | Display key suffixes for identical monitors |
| `ZoneDragMachine.swift` | The pure drag state machine (idle / pressed / dragging, right-click toggle, Shift, ⌘, swallow rules), the ⌘ span anchor, window fitting |
| `ZonesStore.swift` | `zones.json` load, repair, non-overwriting `.bad[.N]` backup, atomic writes, layout CRUD, per-display assignment, editor merge |
| `ZoneDisplays.swift` | `NSScreen` ↔ display keys (reuses `NSScreen.key`) |
| `ZoneDragTap.swift` | The active `CGEventTap` on its own thread and run loop, with an O(1) callback |
| `ZoneWindowMover.swift` | Worker: window lookup, drag confirmation, AX resolution and eligibility, snap, restore |
| `ZoneOverlay.swift` | Click-through per-screen panels drawn with `CAShapeLayer`s |
| `ZonesModule.swift` | The module: lifecycle, session, status menu items, tap retry |
| `ZoneEditor.swift`, `ZoneEditorCanvas.swift`, `ZoneEditorHUD.swift` | The editor window, its canvas (AppKit input, SwiftUI drawing) and its panel |
| `ZonesSettingsPane.swift` | Settings → Zones |

**Threads.** The tap callback runs on the dedicated thread `Cala.zones.tap` and only updates a small state under an `OSAllocatedUnfairLock` and hands off with `async`: no Accessibility calls, no `CGWindowList`, no logging. The serial queue `Cala.zones.worker` performs the window-list queries and external Accessibility work. Main owns AppKit eligibility and placement for Cala’s own windows, the overlay, store, editor and status menu. Pointer updates are coalesced, and the layout strip’s timer runs during AppKit event tracking. A press generation counter makes stale worker results harmless; stopping the module cancels the worker (`ModuleCancellation`) and disables, invalidates and joins the tap thread. Details and the permission analysis are in [zones.md](zones.md).

**Data flow of one drag.** On left-down, the worker records the window under the pointer. Coalesced move checks pass a raw `CGWindowID` to CoreGraphics and confirm a move of at least 3 pt at a stable size. The pending press expires after three seconds or resets on mouse-up. For Cala’s windows, AppKit checks eligibility on main before confirmation. For external windows, movement can confirm the gesture before AX resolution. A tab-strip drag can adopt a single unambiguous detached Chrome/Chromium window. In zones mode, main updates the overlay and picks the target on left-up, which passes through. Placement begins about 40 ms later. For a detached tab, the worker retries AX lookup by the exact adopted window ID for up to 500 ms after the release is handled.

## Panels
- Bars are borderless `NSPanel`s: `nonactivatingPanel`, level `.statusBar`, `canJoinAllSpaces`, `fullScreenAuxiliary`, `stationary`. `BarPanel` never becomes key or main, so clicking it never steals focus.
- Preview and tray panels are also non-activating. `FlyoutPanel` can become key (never main), and `FlyoutController.show` calls `makeKeyAndOrderFront` so native controls receive key focus without activating the application. The shared `flyoutControls()` modifier requests active control appearance and sets explicit switch/slider blue (#007AFF light / #0A84FF dark). `FlyoutSwitchStyle` draws the on/off track with native toggle accessibility; `FlyoutSliderCell` paints the bar while `NSSlider` retains dragging, keyboard and accessibility behavior. These colors remain blue even before key focus or when AppKit considers the app inactive; this is production code, also used by the render harness.

## Hit-testing without SwiftUI gestures
`onHover` and gestures are unreliable in non-key panels. Instead:
1. Each view reports its frame through a `PreferenceKey` (`FramesKey`) in a named coordinate space; each `Bar` stores its own frames.
2. A 0.03 s timer (`tick()`) reads `NSEvent.mouseLocation` and computes which icon is under the mouse.
3. `NSEvent` local monitors handle mouse-down, drag, mouse-up, middle click and scroll on the bar and preview panels.
4. The cursor is set by hand each tick (pointing hand over clickable areas) and `SetsCursorInBackground` is enabled through a private CoreGraphics connection property so macOS honors it while the app is inactive.

## Windows and thumbnails
- Windows come from the Accessibility API (`kAXWindowsAttribute`). `_AXUIElementGetWindow` (loaded with checked `dlopen` / `dlsym`) maps an AX window to its `CGWindowID`.
- If the AX window attribute cannot be read, the list falls back to `CGWindowListCopyWindowInfo` (titled windows only). When AX returns an empty array, that fallback is used only for **hidden** apps. For non-hidden apps with an empty AX array the list is empty: untitled or off-screen CG entries are ghosts of closed windows (Notes keeps them).
- Thumbnails use ScreenCaptureKit (`SCShareableContent` + `SCScreenshotManager.captureImage`), cached in `ThumbCache`. Its mutable state is isolated to `MainActor`; synchronous callers are marshalled to the main queue. Closed-window entries are pruned and least-recently-used eviction keeps at most 100 images. While a preview is open the `SCWindow` handles are resolved once and the visible windows are re-captured every ~100 ms (640 px) in a cancelable task tied to a generation and `shownID`; it ends when the preview closes or switches apps. Capture results are checked again before publication, including whether the window has since minimized.
- `MinimizeWatcher` keeps an `AXObserver` per regular app for `kAXWindowMiniaturizedNotification` and captures that window's thumbnail right then (event-driven, no periodic timer). It is only a fallback: if a thumbnail was taken in the last 5 s (before minimizing) it is kept, because once minimizing starts macOS/Chrome stop drawing video layers. The "before" captures: a global `leftMouseDown` monitor that hit-tests the AX element under the mouse (`AXMinimizeButton`), and `WindowService.minimize` / show desktop (snapshot, then minimize). Cmd+M (switcher setting on) goes through `WindowService.minimize` too, so it also snapshots before minimizing. It is re-synced every 3 s to pick up apps and a late Accessibility grant.
- Closing uses the AX close button. After 0.5 s the fallback rechecks that the same window still exists, is not minimized and has no sheet, raises it, then checks again after 0.15 s that it remains the focused window of the front app before posting Cmd+W.

## Menus and dynamic items
Menus are `NSMenu` popped up above the bar (`position y = barTop + menu height + 4`). `BlockItem` is an `NSMenuItem` subclass that runs a closure. "New…" items are found by reading the app's AX menu bar (File menu = item index 2) and pressing the matching item with `AXPress`. `main.swift` calls `NSRunningApplication.terminate()` directly for eligible **Salir de…** entries. Cala's **Cerrar ventanas** uses `TaskbarModel.ownWindows()` to close titled app windows that are visible or minimized.

## Badges
`DockBadges.read()` walks the Dock's AX tree and reads `AXStatusLabel` for each item, keyed by item title and by `path:<bundle path>`. Refreshed every 2 s on a background queue, with an in-flight guard so slow reads cannot accumulate.

## Drag to reorder
A left press on an app icon is stored (`pressed`) and its click is deferred to mouse-up. After 5 px of horizontal movement the drag starts: `TaskbarModel.dragID/dragScreen/dragX` drive a "ghost" icon drawn by `BarView` at the mouse position (scaled, with shadow), while the real slot is invisible. When the mouse crosses another icon, `TaskbarModel.move` moves the dragged id to the target position in `config.order`; icon positions animate with `.animation` on the item ids. On release the ghost eases into the slot (0.15 s) and is removed. `TaskbarModel.rebuild` sorts items by `order`.

## Peek
`PreviewController.peek`: after ~40 ms of hovering a card it records the front app/window (and the peeked app's focused window), then raises the real window (`WindowService.raise`). Leaving schedules a restore after 150 ms (cancelled by another peek): raise the peeked app's previous window, bring the previous app forward with the AXFrontmost-based `bringFront` helper (the same one show desktop uses), then raise its saved AX window. A thumbnail click or explicit bar activation calls `commitPeek` so nothing is restored. Skipped for minimized windows and windows not in `CGWindowList` on-screen (other Spaces).

## Running-without-windows indicator
Every 2 s a background task (at most one in flight) asks `WindowService.windows(for:)` for each running icon; pids with no windows go to `TaskbarModel.windowless` and `IconButton` draws a dot instead of the bar.

## Show desktop
Hiding apps with `NSRunningApplication.hide()` proved unreliable (System Settings reports hidden ~0.4 s late; Claude re-shows itself; every attempt made macOS activate and unhide another app, causing flicker). It now **minimizes windows through AX** (`kAXMinimizedAttribute`): if any window could be minimized, those windows are appended to the pending set (`desktopMinimized`) together with the original front app; if nothing could be minimized, the stored windows are un-minimized and the front app is brought forward through AXFrontmost. Failed restores remain pending; closed AX elements are dropped. Clicks during capture/minimize/restore are ignored.

## Themes
`BarTheme` holds gradient colors, accent and a forced color scheme. `BarView` draws `theme.background.opacity(barOpacity)` and injects `themeAccent` and `colorScheme` into the environment, so icons, text and `Color.primary` adapt. Flyout and preview roots use `themedPanel()`: one opaque surface (#FFFFFF light / #25272D dark), an 18 pt radius, one 1-pixel border at 2× (black 8% / white 10%) and a shadow. Selected themes add an 8% gradient tint and keep their accent and forced appearance. Every flyout has the same 18 pt content inset, including the calendar. Usage provider sections use `flyoutSection()` with a subtle #F4F5F7 / #2D3037 fill and no border. `FlyoutStyle` defines secondary text colors (#626570 / #B8BDC8), quota bar colors and primary quota numbers (amber #C77700 / #FFB340 below 25%; red #D70015 / #FF6961 below 10%). Green is reserved for healthy quota bars. `TrayHighlight` gives all tray controls a 14% white hover fill and 10% white hairline in dark mode. Settings still follow the system appearance.

## Settings window
`SettingsWindowController` creates one `NSWindow` (titled, full-size content view, transparent titlebar) hosting `SettingsView` (sidebar + `PaneBody`). It follows the system appearance, not the bar theme. Bindings write to `ConfigStore` (Claude & Codex folder drafts apply on submit, focus loss or leaving the detail), which saves atomically and publishes, so the bars update live. Decoding recovers missing or mistyped fields individually and clamps the bar's numeric preferences to supported ranges; the Dock backup fields are kept verbatim. A file that cannot be decoded is preserved as `config.json.bad`; if preservation fails, saves are disabled to avoid overwriting it. Dock adoption is skipped after a load failure or recovery of invalid fields. Launch flags: `--settings` opens it at start; `--snapshot <dir>` renders the pages, detail and off-module variants, welcome, editor and layout-strip fixtures to PNG using an offscreen `NSHostingView`, then exits without starting modules.

## Window switcher
`WindowSwitcher` is the Switcher module: `start()` installs a `CGEventTap` (HID level, head insert, active filter, main run loop) for keyDown/keyUp/flagsChanged; it needs Accessibility. `stop()` cancels any open switcher, removes the tap, the retry timer and the panel. While it runs, `ensureTap()` runs at start and every 3 s, retries enabling a disabled tap, and removes the run-loop source and invalidates/recreates the port if it is invalid or cannot be enabled. Timeout/user-input disable notifications cancel an active switcher before recovery.

The callback decides which events to swallow and defers switcher actions to the main queue. Window collection runs on a background queue with one collection in flight; generation checks discard canceled results, and navigation / modifier release received during collection are applied when it completes. While it is active, only Tab, Shift+Tab, arrows, Esc, Return, Backspace and typed letters/digits/space// pressed with the trigger modifier still held are swallowed; the release is recorded synchronously in the callback, so from then on every key (including during a slow collection, whose pick is committed when the list arrives) reaches the app. Only keyUps matching swallowed keyDowns are swallowed, including after the panel closes; the set is cleared whenever the tap is re-enabled or recreated, and a passed-through non-repeat keyDown drops its keycode from it. Option+Tab (or optionally Cmd+Tab) opens it, navigation changes the selection, and releasing the trigger modifier commits. The list comes from `CGWindowListCopyWindowInfo(onScreenOnly)` z-order matched to AX windows, followed by remaining AX windows of regular apps (including minimized windows and windows on other Spaces), capped at 20. Thumbnails use `ThumbCache`; picking calls `WindowService.raise`.

Inside the open switcher, typed characters (read with `NSEvent.charactersIgnoringModifiers`, so Option does not change them) feed `SwitcherModel.query`: `all` keeps everything collected and `windows` is the filtered list (title or app name), re-filtered on every change. While the query is empty and no search has started, W / Q / M are actions on the selected card (W: `WindowService.close` off the main thread; Q: `NSRunningApplication.terminate` and every card of that app removed; M: `WindowService.minimize`, or un-minimize through AX, flipping the card's `minimized` flag in place). `/` or any other character starts the search (`searching`), after which W/Q/M are plain letters. Esc clears the search first, then cancels. Any change to the list re-sizes and re-centers the panel; card size comes from `SwitcherLayout` (max 360 px wide, shrunk so the grid fits 92 % of the screen width and 85 % of its height).

Cmd+M interception is enabled only with the switcher setting. The callback only checks that another app is frontmost, swallows the key (repeats included) and moves the work to a background queue: it checks the focused window, a false fullscreen attribute and an enabled AX minimize button (0.25 s messaging timeout per element), then calls `WindowService.minimize` (snapshot, then minimize; pressing the button if the window id is unknown). If a check fails or times out before acting, the original Cmd+M is re-posted to the app with `postToPid`, tagged through `eventSourceUserData` so the tap ignores it. Once the minimize is issued nothing is re-posted, even on a timeout (unknown result), so one Cmd+M never minimizes two windows. The global AX messaging timeout is also set to 0.25 s at launch; helpers can use a more specific timeout.

## Hiding the Dock
This belongs to the Bar module (see [Modules](#modules)). `DockControl` writes `autohide=true` and `autohide-delay=1000` in `com.apple.dock` with `CFPreferencesSetValue`, then runs `killall Dock`. The first time it saves the previous values in `config.json`; restoring writes them back (nil removes the key). At a fresh process launch it re-applies the choice or adopts an already-hidden Dock; reopening the running instance only shows Settings. On quit it restores when `restoreDockOnQuit` is on. A main-queue DispatchSource handles SIGTERM by calling `NSApp.terminate`, so normal termination cleanup also runs for that signal; crashes and force-quit cannot run it.

## Space reservation
Only when auto-hide is off and only on the primary screen: every 0.6 s, if the focused window extends below the bar top, its height is reduced through AX. Skips full-screen windows and does nothing while a mouse button is pressed. Window IDs whose resized height fails a delayed verification are remembered and skipped for the rest of the process lifetime. This is an approximation, not a true reserved area.

## Tray internals
- Battery: `IOPSCopyPowerSourcesInfo`, refreshed instantly by `IOPSNotificationCreateRunLoopSource` (macOS calls back on plug/unplug/charge changes; no polling).
- Wi-Fi: `CoreWLAN` (`powerOn`, `rssiValue`, `ssid`, `scanForNetworks`, `associate`). SSID access needs Location permission. Signal level maps -90…-50 dBm to 0…1 and drives `Image(systemName: "wifi", variableValue:)`. Scans and network association run in the background; failed association opens Wi-Fi settings on the main queue.
- Volume: CoreAudio, property `vmvc` (virtual main volume) and `mute` on the default output device.
- Bluetooth: private `IOBluetoothPreference{Get,Set}ControllerPowerState` plus `IOBluetoothDevice.pairedDevices()`. A device toggle opens connections asynchronously on the main queue (callback on main); the synchronous `closeConnection()` runs on a background queue.
- Brightness: private `DisplayServicesGetBrightness` / `SetBrightness`, loaded with `dlopen`.
- Keyboard: Carbon Text Input Sources (`TISCreateInputSourceList`, `TISSelectInputSource`).
- Users: the profiles panel loads names and photos on a background queue (`dscl` for names, `JPEGPhoto` or `Picture` for photos). `Users.switchTo` loads the PRIVATE `login.framework` symbol `SACSwitchToUser` with checked `dlopen`/`dlsym`. On a background queue it reads the local user's OpenDirectory record (RecordName, UniqueID, GeneratedUID, RealName, NFSHomeDirectory, PrimaryGroupID, UserShell, RecordType, AppleMetaNodeLocation, JPEGPhoto and masked Password). The dictionary uses `dsAttrTypeStandard:*` keys and array values; RecordName[0] must match the non-empty target short name and binary plist serialization must succeed before calling the API. loginwindow uses this record to preselect the target, including users without an open session. Return 0 means only that loginwindow received the request; the switch is asynchronous. The same background queue polls the PRIVATE SkyLight `SLSCopySessionList` every 0.25 s for up to about 3 s, checking the original session's `kCGSSessionOnConsoleKey`. Lookup, validation, API or verification failure triggers one Ctrl+Cmd+Q lock fallback on the main queue. A main-queue guard ignores further switch requests until completion. Success is sticky for each attempt; the main-queue fallback rechecks the attempt and success state. A continuous monotonic clock measures the timeout, including suspension: verification delayed beyond 6 s is logged as unknown, probably switched, and does not lock the screen. `SLSSessionSwitch*` calls are blocked for non-Apple callers and are not used. Both login.framework and SkyLight are PRIVATE APIs that may break in any macOS update.
- Low Power Mode: a background `Process` runs `/usr/bin/osascript -e` with `do shell script "pmset -a lowpowermode …" with administrator privileges` (password prompt each time). The toggle refreshes the actual system state on completion and every 2 s; no AppleScript executes on the main thread.

## System panel
`SystemMonitor` samples process CPU and total CPU over the same window. It publishes a `ProcessReading` only when total CPU is within 0–100%, process values are finite and nonnegative, and their sum is at most five percentage points above the total. When validation fails, the sampling counters advance and the last valid reading stays available until it expires, four seconds after capture. The CPU meter, breakdown and attributed action use that same reading. Without a fresh valid reading, the meters and list show loading skeletons, as does the guidance card when it is waiting for attribution. `SystemLoadingPulse` uses a static placeholder when Reduce Motion is enabled.

The monitor tracks continuous critical memory pressure and thermal state separately. `SystemRules` uses those durations for red severity and the smoothed CPU duration for sustained-load guidance. App processes are grouped by bundle path, and multiple running instances leave the group without a quit PID.

`SystemPanelLayout` budgets the list within the 520 pt panel height. It starts with seven rows and subtracts one for a guidance card and one for maintenance. CPU and memory breakdowns reserve one slot for the remainder.

`SystemPane` passes live monitor and restart state to `SystemPanelView` as a model and callbacks. `SystemRules` and `RestartRules` work on values with Foundation. The SwiftUI views render their results, and AppKit actions run through `SystemAdvice` and `RestartAdvisor`.

`SystemRules` groups tool rows by name and splits their details by launcher. `SystemMonitor` probes `/bin/ps` in the background only while **Sistema y otros** is expanded. The pure rules strip other accounts' executable names, skip processes already represented in visible rows and use CPU and RSS as weights for an estimated split of the existing remainder. The probe leaves the parent total and guidance tied to the validated reading. Panel actions recheck the current reading, and quitting through `SystemAdvice` still asks for confirmation.

`RestartAdvisor.swift` bounds the reasons viewport and shows a scroll hint when reasons extend below it. The permission message and action buttons sit outside the scroll area.

## Code signing and permissions
Ad-hoc signed with a fixed designated requirement (`designated => identifier "local.cala"`) so macOS keeps Accessibility / Screen Recording grants across rebuilds. Without it, every rebuild invalidates the grants. Private CoreGraphics cursor symbols are resolved with checked `dlopen` / `dlsym`, rather than mandatory link-time symbols. Ad-hoc builds also use the hardened runtime with `packaging/Cala.entitlements` (Apple Events, calendars, location); every `dlopen` targets Apple system frameworks, which library validation allows.

**Keychain helper.** The login keychain binds an item to the cdhash of the program that may read it, and an ad-hoc Cala has a new cdhash every build. So `MailKeychain` never calls SecItem itself: it runs `Contents/Helpers/cala-keychain` (C, `Helpers/cala-keychain/main.c`) with the request on stdin (`get|set|delete`, account id, then the password for `set`) and reads the password from stdout; exit 0 ok, 1 not found, 2 denied/cancelled, 3 Keychain error, 64 bad request, 77 caller is not this bundle's app, 78 caller could not be verified (an anti-race hint was unavailable; Team ID mode only). The binary is prebuilt once (`scripts/build-keychain-helper.sh --yes`, universal, ad-hoc, hardened runtime, identifier `local.cala.keychain`), committed as `packaging/Helpers/cala-keychain` with its SHA-256 and per-arch cdhashes in `cala-keychain.cdhash`, and copied without re-signing by `build.sh`, which fails unless `scripts/verify-keychain-helper.sh` matches every slice, and on any bundle id / signing identifier / Team ID inconsistency. Developer ID builds re-sign the copy with the identity (notarization requires it); the Keychain then trusts the team id. Rebuilding the committed binary costs every user one more prompt per account (maintainer rules: [release.md](release.md), "Ayudante del Llavero"). Exit 77 maps to `MailFailure.keychainRestart` (typically a Cala that kept running after its bundle was replaced: "restart Cala") and 78 to `MailFailure.keychainUnverified` ("restart your Mac; reinstall if it persists"); both need user action and are not retried.

Caller check, before the request is read. Mandatory in every mode (any failure gives 77): the helper sits at `<bundle>/Contents/Helpers/cala-keychain`, its own running code validates (`SecCodeCheckValidity(self)`; so replacing its file mid-run cannot downgrade it), the bundle has a CFBundleIdentifier, the parent's code can be located and `SecCodeCheckValidity` succeeds against `identifier "<that id>"` (plus `anchor apple generic and certificate leaf[subject.OU] = "<its own team>"` when the helper has a Team ID), and the parent is that bundle's main executable. Anti-race hints: the parent's audit token must carry the pid version the kernel recorded at fork (private `proc_pidinfo` flavor 17, trusted only when its layout matches the helper's own audit token) and must not change during the check, so an `exec` after spawning gives 77. Without a Team ID, a hint the OS cannot provide is skipped (pid lookup instead); with one it gives 78. What it protects: **ad-hoc** (the free build), nothing against a local attacker, who can sign any program with any identifier and copy the helper beside it; it stops accidental and casual callers. **Developer ID**: only code signed by that team is served; it does not stop code already running as Cala, anything that team signs with Cala's identifier, or anyone who can read the login keychain directly. **Migration of pre-helper items.** Items saved by older builds (account = email) trust only that build; the helper cannot delete them (`errSecInvalidOwnerEdit`, verified in a disposable keychain) nor change their ACL. `MailCredentialStore` therefore reads the helper's own item `v2:<email>` first; when it is missing it reads the old item (up to two macOS windows: ACL, then partition) and copies it into `v2:`; when `v2:` exists but cannot be read (denied or broken) it falls back to the old item without copying; a helper refusal (77/78) is reported. New and changed passwords are written to `v2:` only; removing an account deletes `v2:` and leaves the old item (manual cleanup). `MailKeychainGate` keeps one UserDefaults key per account (`mailKeychainMigrated.<email>` = helper cdhash), written only after a successful `v2:` write or read; the explanation window shows while any enabled account lacks it and announces two windows per such account.

**SECURITY.** `install.sh` publishes the shared bundle at `/Applications/Cala.app`. The parent directory is root:admin and writable by administrators. The installer stages the copy with `ditto` under `sudo`, sets bundle ownership to root:admin, removes ACLs and group/other write access, verifies the signature and atomically publishes it before stopping Cala in the installing session. Developer installs previously used `~/Applications`. Another user could replace a bundle through a writable parent such as `/Users/Shared` and inherit its Accessibility or Screen Recording grants. Use the installed copy for permissions and login. After a move, each account grants access again for the new path.

`BundleUpdateMonitor` captures the running build number and checks the on-disk Info.plist at startup, session activation, wake and every five minutes. A candidate must have the same bundle ID and executable name, an executable file, and a higher build number stable for five seconds. Cala waits for an active session without an ongoing drag, Zones interaction, open editor, Settings, onboarding or modal dialog. If AppKit cancels termination, Cala retries in one minute. Once termination is confirmed and modules have stopped, the helper waits up to a minute for the process to exit and then opens the new build through Launch Services.

## Debug log
`~/Library/Application Support/Cala/debug.log` records the `modules:` and `module …:` lines, `zones:` lines (layouts loaded, tap state, snaps, ignored drags), clicks (app, window count, trust state), close attempts, show-desktop passes and diagnostics, without window titles or window dumps. Writes are serialized on a dedicated queue; when the existing file exceeds 1,000,000 bytes it rotates to `debug.log.1`, replacing the previous backup.

`applicationShouldHandleReopen` opens the Settings window, so launching the app again (Spotlight, Launchpad) while it runs gives access to the settings and the Quit button.

## AI plan usage
`Usage.swift` owns detection, parsing, bounded child processes, an ephemeral URLSession, local FSEvents watchers and a non-secret cache. A serial utility queue owns service state; separate workers perform fetches, one in flight per provider. Only value snapshots are published on main and mirrored by `TaskbarModel.usage`. The tray and flyout UI live in `BarView.swift` and `Flyout.swift`; Settings → Integrations → Claude & Codex opens the integration’s detail. The Tray row opens the same detail with a back row to the Tray. `UsageTrayView` reports only `trayUsage` (`__t_usage_combined`) for the whole Claude/Codex group, in its configured tray position. The existing frame-based hover/click pipeline opens one `UsagePane`. `UsageState.orderedWindows` orders provider windows as session, weekly all-models, scoped weeklies, then other durations ascending; the tray summary and flyout both use this order. Codex readings retain optional `durationMinutes`; old caches without it infer known categories or numeric-hour titles, preserving input order for ties and unknown durations. Plan identifiers are humanized in the presentation layer (`Pro Lite`, `Max 5x`, `Max 20x`, etc.); cache and service values stay unchanged. Provider marks are independent SwiftUI Shapes: a solid-center spark with nine uneven tapered rays and a cloud/terminal prompt; no downloaded logo assets.

Detection runs on startup, about every five minutes, on relevant settings changes and whenever Settings opens. Folder precedence is custom setting → login-shell environment → `~/.claude` / `~/.codex`. One `/bin/zsh -lc` invocation reads folder variables and PATH with a three-second timeout and null stdin; only fields following the last unique marker are accepted, excluding profile banners. Executables are resolved per user across standalone releases, common package-manager paths, PATH and system/user application folders.

Claude credentials come from `/usr/bin/security find-generic-password` (three-second timeout), service `Claude Code-credentials`, account `NSUserName()`, or `<configDir>/.credentials.json`. For an environment-configured directory, service candidates try the first eight hex characters of SHA-256 of the raw NFC environment value before the standardized path hash. The unsuffixed name is tried only for the default directory or when no custom folder or environment override is set; a custom setting resolving to `~/.claude` uses the unsuffixed name. The secure-storage override and sanitized `claude-code-user` account fallback are honored. This naming was verified against the extracted credential helper of Claude Code 2.1.286. No Security-framework item lookup is used, avoiding prompts tied to changing ad-hoc identities. Expired credentials require the user to open Claude Code. A 401 rereads credentials and retries once only when the token differs. A final 401 suppresses further API requests until the credential expiry value or an in-memory token fingerprint changes. Disabled providers skip credential/auth checks. The read-only OAuth usage endpoint prefers `limits[]`, falling back to legacy windows. ISO dates accept fractional seconds and offsets.

Codex detection checks `auth.json` existence. The preferred live source is a short-lived `codex app-server` JSON-lines exchange (`initialize`, `initialized`, `account/rateLimits/read`), bounded to ten seconds and terminated/reaped after the reply; unrelated notifications are ignored. If no executable exists, the HTTP fallback reads ChatGPT tokens only for `backend-api/wham/usage`. FSEvents watches only Codex sessions and filters incoming paths, while a file-descriptor watcher targets just Claude’s usage JSON and rearms after atomic replacement (a missing file is checked by cheap maintenance). Rollout lines are prefiltered for `token_count`; on changes, metadata selects the newest three rollout files and only their final 256 KiB are read. The greatest valid token-count event timestamp competes with live fetch completion time; the newer reading wins. Claude's optional statusLine script uses built-in JXA via osascript, atomically writes only rate limits plus a timestamp, and preserves an existing statusLine. Settings changes require an existing Claude config folder, preserve other keys, and atomically replace JSON without escaping slashes. The first settings backup is created only when no backup exists and is never overwritten. An already-owned statusLine leaves the settings bytes and backup unchanged. Cala records the installation directory separately. A missing or invalid preference leaves Claude settings untouched. On an edit, Cala follows symlinks to the settings file, preserves its POSIX permissions and rereads changed bytes before reevaluating ownership and retrying. Uninstall stops if it cannot complete tracked statusLine cleanup. See [configuration.md](configuration.md#claude--codex-settings) for the file and backup names.

Startup and wake fetches require a visible bar (or auto-hide disabled); a hidden startup renders cached and local readings only. Other fetch triggers are bar reveal and flyout open, with minimum ages of 120 seconds for Claude and 60 seconds for Codex. A recent Codex local reading suppresses fetching too. Claude local readings retain API scoped windows and their API timestamp; local statusLine events cannot extend the 120-second API freshness interval. Repeated non-200/transport failures back off from 120 seconds exponentially to 30 minutes separately from 429 cooldowns. Manual refresh bypasses age/error-backoff limits with a 15-second floor after failures, and never bypasses cooldown, the final-401 credential gate or the in-flight guard. Both HTTP integrations reject redirects, including same-origin redirects, before forwarding bearer credentials. No timer fetch runs while hidden. A visible, non-auto-hidden bar refreshes every 15 minutes plus up to 90 seconds of jitter. Passed reset timestamps display zero used locally and permit one revalidation per window/reset, subject to the minimum interval. HTTP 429 honors Retry-After (numeric or HTTP date), at least 60 seconds, then exponentially backs off to at most 30 minutes; success clears backoff. Cooldowns and last readings are persisted in `usage-cache.json`, partitioned by config folders. Logs use `usage:` with status, duration and cooldown, never credentials or account identifiers.

**Private interfaces / terms:** Anthropic OAuth usage, ChatGPT WHAM usage, Codex app-server schemas and rollout/statusLine fields are private or undocumented integration surfaces and may break at any time. This feature makes read-only use of the user's own signed-in credentials; it never requests token refresh, rotates tokens, or writes credentials. Provider terms and access policies still apply; availability is not guaranteed. Only usage values, plan labels, timestamps and folder paths are cached.

## Calendar events
`CalendarService` is separate from `TaskbarModel`: only the clock flyout and Calendar settings observe it. Construction registers change/activation observers but never creates an `EKEventStore`; `open(config:)` is the sole user-intent entry point that may request full access. Requests are admitted on main only while enabled. A serial utility queue owns the store, fetches calendar/source metadata and bounded-range events, and converts EventKit objects to value snapshots. Main-thread revision checks reject stale results after settings changes or disabling. The store never writes events.

The range includes ongoing/all-day events, excludes canceled/ended events, and honors excluded calendar IDs before constructing the predicate (an empty selection never falls back to all calendars). EventKit changes and app activation refresh without requesting permission; the visible list also refreshes every minute. Denied/restricted/write-only states render a privacy link. `CalendarLogic` handles grouping, current/next timed highlights and allowlisted web meeting links. All-day and recurring/multi-day occurrences retain their EventKit start/end dates; ongoing multi-day events are grouped under Today. The list viewport adapts to available screen height, and provider-independent `flyoutSection()` cards keep the shared opaque surface.

Only enabled, Join button, range and excluded calendar IDs are persisted in config with per-field recovery. Event titles, notes, locations and URLs remain in memory and are never logged or cached. Account sign-in/sync belongs to macOS Internet Accounts. Event navigation uses an undocumented Calendar URL with an app fallback; exact event/date selection is best effort. The scratchpad render harness injects a preview service and a store factory that fails if real access is attempted. See [Apple’s full-access API](https://developer.apple.com/documentation/eventkit/ekeventstore/requestfullaccesstoevents(completion:)) and [EventKit store](https://developer.apple.com/documentation/eventkit/ekeventstore).
